Atomicity, recovery reasoning, and two-session concurrency

Meetings 23–25. Open two independent PostgreSQL connections A and B to the same teaching database. In each use SET search_path TO course32;. Finish every experiment with COMMIT or ROLLBACK before beginning the next.

Meeting 23: atomic transfer and simplified WAL

  1. Read the accounts: 1=100, 2=100. BEGIN; debit account 1 by 25; credit account 2 by 25; COMMIT. Verify 75,125 and conserved total 200.
  2. Begin another transfer but attempt a negative balance. Record the error and ROLLBACK. Verify the committed balances survive and the failed transaction makes no partial change.
  3. Reset to 100 each using a committed UPDATE when both sessions are idle.

Paper recovery model: Assume steal/no-force, undo/redo logging with before/after values, and a durable log prefix. Initial A=100, B=100. Durable log: START T1; T1 A:100→80; T1 B:100→120; COMMIT T1; START T2; T2 A:80→70; CRASH. Disk at crash has A=70,B=100. Identify winner/loser, redo committed updates and undo incomplete updates, and derive the recovered state. Explain why the log must be durable before an affected page is flushed. This is a teaching model, not a claim that PostgreSQL uses this exact undo algorithm.

Meeting 25: snapshots and guarded writes

  1. A: BEGIN ISOLATION LEVEL READ COMMITTED; SELECT balance FROM accounts WHERE id=1. B: update that account by +10 and commit. A: repeat the SELECT, then ROLLBACK. Record the new value.
  2. Repeat with A at REPEATABLE READ; establish its snapshot with the first SELECT before B’s committed update. A’s second ordinary SELECT keeps its earlier value.
  3. Reset stock item 1 to quantity=1. A: BEGIN; UPDATE stock SET quantity=quantity-1 WHERE id=1 AND quantity>0 RETURNING quantity. B: issue the same update in its own transaction. After observing the wait, commit A. Under READ COMMITTED B returns no row. Commit B and verify quantity=0.
  4. Explain why reading quantity into the application and later writing an absolute value can lose updates. State what the guarded update guarantees and how the application should interpret zero affected rows.

Submit: exact execution order, values, transaction boundaries, graphs, and invariants. Stretch: investigate a serialization failure and explain why retrying just the last statement is insufficient.
