Meetings 17–18. The original stored-program slides include MySQL examples. This supplement deliberately uses PostgreSQL PL/pgSQL to match the repository’s runnable database. Do not mix DELIMITER or MySQL handler syntax into these scripts.

Meeting 17: transfer function

Implement your own function from the requirements below. Instructor reference solutions are distributed separately. Required signature: course32.transfer(from_id integer,to_id integer,amount numeric). It must reject nonpositive amounts, identical accounts, absent accounts, and insufficient funds; lock accounts in ascending ID order; debit and credit in the caller’s transaction.

  1. Write the input-validation branches and explain why NULL must be handled explicitly.
  2. Implement locking and updates. Explain why checking balance outside the transaction is unsafe.
  3. From balances 100/100 transfer 25 from 1 to 2. Expect 75/125.
  4. Try 999, a negative amount, the same account twice, and an absent recipient in separate transactions. Roll back each failed transaction and verify balances unchanged.
  5. Call a successful transfer inside BEGIN, inspect balances, then ROLLBACK. Explain why a function should not independently commit the caller’s unit of work.

Meeting 18: audit trigger

  1. Design an audit row containing account ID, old/new balance, and timestamp. Implement and install your own AFTER UPDATE trigger.
  2. Perform one committed transfer. Expect two audit rows, one per account update.
  3. Attempt a transfer then ROLLBACK. Verify no persistent balance change or additional audit row from that transaction.
  4. Choose mechanisms for nonnegative balance, existing recipient, unique email, seat capacity across rows, and logging every successful balance update. Explain why the audit trigger is different from a CHECK.
  5. Discuss the limits: ordinary transactional audit rows roll back with the transaction and are not a tamper-proof compliance log.

Submit: function/trigger SQL, a six-case test matrix, and observed persistent state. Stretch: add a transaction reference and describe an idempotency design for retrying requests.
