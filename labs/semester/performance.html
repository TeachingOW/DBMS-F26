Storage, indexes, joins, and optimizer laboratory

Meetings 19–22. Existing decks supply the theory. Use performance-setup.sql after the shared setup. It adds 100,000 deterministic purchases to the teaching schema. Run once in a fresh fixture.

Meeting 19: storage and I/O worksheet

Assume fixed 100-byte records, 8,000 usable bytes/page, no spanning or overhead, and 100,000 records. For sorting assume 11 buffer pages, initial runs of 11 pages, and merges of at most 10 runs; count both reads and writes on every pass, including final output.

  1. Compute records/page and total pages.
  2. Compute initial runs, merge passes, and total page I/Os.
  3. A B+ tree has three index levels including leaves. Under a cold-cache model, estimate page reads for one matching tuple stored on one heap page. Explain how caching the root changes this estimate.
  4. Explain why an unclustered range lookup returning most rows can cost more than a sequential scan.

Meeting 20: index experiment

  1. Run ANALYZE. Capture EXPLAIN (ANALYZE, BUFFERS) for customer_id=42 and for status='paid'.
  2. Create a B-tree index on (customer_id,purchased_at). Repeat both queries three times. Record the median execution time, scan type, estimates/actual rows, and buffer hits/reads. Do not claim a cold-cache comparison merely because this is a new query.
  3. Test customer_id=42 with a date range, then a date-only predicate. Explain the leading-column effect without assuming the planner must choose an index.
  4. Compare EXTRACT(YEAR FROM purchased_at)=2026 with a half-open date range. Discuss an expression index as a different design.
  5. Measure index size with pg_relation_size; explain write and storage costs.

Meeting 21: join costs

R has 1,000 pages, S has 200 pages, and M=22 buffer pages. Ignore final output writes. For page nested-loop use bR+bR×bS. For block nested-loop reserve two pages and use bOuter+ceil(bOuter/(M−2))×bInner. For a two-pass Grace hash join assume partitions fit, no skew, and cost 3(bR+bS).

  1. Calculate page nested-loop cost for both outer choices.
  2. Calculate block nested-loop cost for both choices.
  3. Calculate hash-join cost and state the assumption whose failure would require another pass.
  4. Inspect a join between perf_purchases and perf_customers. Explain why textbook cost units are not elapsed milliseconds and why small/selective inputs may favor nested loops.

Meeting 22: optimizer investigation

  1. Compare the estimate and actual rows at every node for a customer/status join query.
  2. Filter to a single customer, then to all paid purchases. Record whether the join algorithm changes; “no change” is a valid observation.
  3. Prove result equivalence for a rewrite with EXCEPT in both directions, then compare plans.
  4. Recommend indexes for a workload of 70% customer histories, 20% monthly summaries, and 10% inserts. State the data distribution and measurement limits.

Submit per meeting: worksheet or plans plus evidence table. Exact plan shape and speedup are not graded; correctness of interpretation is. Stretch: introduce skew and compare stale versus refreshed statistics.

Reference: PostgreSQL EXPLAIN guide. ANALYZE executes the query; the exercises above use SELECT statements.
