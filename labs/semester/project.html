Project milestones and cumulative exercises

Meetings 15, 16, 31, and 32. Keep the instructor’s existing grading policy. The rubric below is a feedback rubric within each existing project component, not a new course-weight scheme.

Existing course project: Use the instructor-assigned project as the primary project. These milestones and generic exercises supplement that assignment; they do not replace its rubric or add a second required project. Where it already supplies an equivalent design, SQL, or concurrency task, submit that evidence once. Follow the assigned project’s database dialect rather than mixing it with the PostgreSQL practice fixture.

Milestones

  • Meeting 4: scenario, requirements, ER model, and scope.
  • Meeting 12: normalized schema, constraints, seed data, and dependency argument.
  • Meeting 15: query portfolio workshop.
  • Meeting 16: midterm project due and feedback.
  • Meeting 28: working database application and failure tests.
  • Meeting 31: performance and restore evidence.
  • Meeting 32: final demonstration and submission.

Meeting 15: midterm portfolio

10 minutes triage, 15 worked edge case, 60 implementation/peer review, 15 reporting. Submit at least ten purposeful queries: two multi-table joins including an outer join; two grouped reports; an anti-join; a correlated query; a set operation; a window query; a recursive query on a meaningful hierarchy; and one business-specific report. Use a separate supplied hierarchy if recursion is unnatural for the project. Include expected results and tests for empty groups, ties, NULLs, and duplicate-producing joins.

Meeting 16: defense and individual debugging

10-minute quiz/retrieval, 15-minute common-error discussion, 60-minute rotating project defenses, 15-minute revision plans. Use six 10-minute stations/slots or parallel peer review; larger cohorts use recorded demonstrations plus individual questions.

Debug this report: an event LEFT JOINs bookings, filters paid=true in WHERE, groups by title only, and uses COUNT(*). Identify the correctness problems and repair them using the shared fixture. Expected paid counts are SQL 2, Design 1, Data 1, Graph 0. Explain how two events with the same title change the grouping requirement.

Meeting 31: integration clinic

  1. Fresh setup: a peer can recreate the schema and data from your instructions.
  2. Correctness: keys and constraints reject invalid state; query outputs match fixtures.
  3. Atomicity: a forced error leaves no partial update.
  4. Concurrency: two competing requests preserve a stated invariant.
  5. Security: user values are bound; the runtime role has only required privileges; credentials are absent from source.
  6. Performance: one measured plan/index comparison includes row counts and interpretation.
  7. Recovery: restore into a new database and compare both counts and business totals.

Meeting 32: demonstrations and cumulative synthesis

10 retrieval, 15 setup/rubric, 60 demonstrations or rotating stations, 15 individual reflection. Students waiting for a demo solve: (1) an FD/key proof; (2) a NULL/outer-join counterexample; (3) an index choice with workload assumptions; (4) a two-transaction conflict graph; (5) a crash-versus-backup distinction. Use the corresponding workbook inputs rather than undefined schemas.
