Database application and secure booking lab

Meetings 27–28. Use Python and PostgreSQL; one programming language is sufficient. Start with booking_app.py, install psycopg[binary], and configure PGHOST, PGPORT, PGDATABASE, and PGUSER using your normal PostgreSQL environment. The starter prompts for PGPASSWORD if it is not set; do not commit credentials. The database must already contain setup.sql.

Meeting 27: implement and trace

  1. Read the starter and mark the SQL statements, parameter values, transaction boundary, and error paths.
  2. Run python booking_app.py 5 104 to book Eli into Graph. Explain the composite-key protection against a repeated request.
  3. Add a read-only list-events command and a cancellation command. For cancellation lock the same event row before changing bookings; all application writers must follow the same locking convention.
  4. Return clear user outcomes for a missing student/event, duplicate booking, and sold-out event. Report success only after commit.
  5. Use parameter binding for all user-supplied values. Explain why identifiers such as column names require a separate allowlist/composition mechanism.

Meeting 28: acceptance and concurrency tests

Use a fresh fixture or record the rows created by each test. Graph has capacity 1 and starts empty. Remove only your test booking before the last-seat experiment.

  1. Successful booking: exactly one new row, and the student appears once in the event roster.
  2. Duplicate request: a second identical command returns “already booked” and does not create another row.
  3. Missing student and missing event: clear error and no inserted row.
  4. Quoted names: insert a test student through a parameterized helper using O'Brien and then the literal text ' OR '1'='1. Verify exact storage and that unrelated rows are unaffected.
  5. Last seat: run two processes for different students against event 104. One succeeds and one reports full; verify exactly one booking. Explain how the event-row lock serializes these writers at READ COMMITTED.
  6. Rollback: temporarily raise an exception after INSERT but before leaving the transaction context. Verify no booking persists and no success message appears.

Submit: application, setup instructions, six-case evidence matrix, and transaction explanation. Stretch: add a unique request ID for idempotent external retries; explain why blindly retrying a committed-but-unacknowledged payment is unsafe.

Reference: Psycopg transaction contexts.

This is a classroom concurrency contract: it assumes all booking writers lock the event row and event capacity is not changed concurrently outside that contract. Discuss enforcing the contract with restricted permissions or a stored routine in a production design.
