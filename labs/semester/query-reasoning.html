Query reasoning and relational algebra workbook

Supports meetings 6–10. Use the shared fixture and SET search_path TO course32;. Each meeting has its own task set; do not try to finish all five in one class.

Meeting 6: joins and multiplicity

  1. Produce (student_name,event_title) for every booking. Predict six rows.
  2. List every student with their booked event if any. Keep Eli, who has none. Predict seven rows.
  3. Return every event and only its paid bookings. Compare a payment predicate in ON with one in WHERE. Explain why Graph disappears in the second version.
  4. Join students and events without the bookings relation. Predict the cardinality and explain why DISTINCT cannot repair the missing relationship.

Meeting 7: aggregation

  1. For every event, report total bookings, paid bookings, and paid revenue. Preserve Graph with zeros.
  2. Explain COUNT(*) versus COUNT(b.student_id) after a left join.
  3. Find events with at least two bookings using HAVING; classify paid revenue as zero, below 30, or at least 30 using CASE.
  4. Add another one-to-many relation on paper and show how joining it before aggregation can double revenue. Repair with preaggregation.

Meeting 8: subqueries and sets

  1. Find students with no bookings using NOT EXISTS.
  2. Find students booked in both SQL and Design using INTERSECT, then using two EXISTS predicates.
  3. Find students booked in every event in RequiredEvent; explain the double NOT EXISTS pattern.
  4. Run SELECT id FROM students WHERE id NOT IN (SELECT student_id FROM booking_probe). Explain the empty answer and repair it. Does NOT EXISTS have the same NULL behavior?

Meeting 9: algebra

Use S=students, E=events, B=bookings. Classical relational algebra uses sets.

  1. Write selection and projection for titles of events with fee ≥20.
  2. Write an algebra expression for names of students booked into SQL.
  3. Express students without bookings using difference. Ensure the two operands have compatible attributes.
  4. Express students in both required events using intersection or division.
  5. Project event_id from B using SQL with and without DISTINCT; explain the relationship to algebraic projection.

Meeting 10: equivalence workshop

  1. Push a fee predicate below an inner join and verify the same tuples.
  2. For E LEFT JOIN B, move B.paid = true from ON to WHERE. Use Graph as a counterexample to equivalence.
  3. Express students with any booking using EXISTS (a semijoin) and a join. Explain why the latter needs duplicate elimination to return one row per student.
  4. Show why pushing a filter on aggregate revenue below GROUP BY is generally invalid. Distinguish it from a filter on the grouping key.

Submit each meeting: numbered answers, runnable SQL where applicable, predicted and actual rows, and one counterexample. Stretch: explain the result of the “every required event” query when RequiredEvent is empty.
